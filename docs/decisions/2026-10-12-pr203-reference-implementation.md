# 2026-10-12 — Does sv2-spec PR #203's reference implementation change silent-pool?

**Trigger.** [PR #203 comment 6109310390](https://github.com/stratum-mining/sv2-spec/pull/203#issuecomment-6109310390) (warioishere, 2026-10-11): runnable `0x0003` code — `extensions_sv2` messages/TLV/payout math ([warioishere/stratum#1](https://github.com/warioishere/stratum/pull/1)), an SRI JDC ([warioishere/sv2-apps#3](https://github.com/warioishere/sv2-apps/pull/3)) — pinned to the PR's only commit `47dbedd`, run on mainnet against Blitzpool's JDS, plus two unrelated SRI bugs ([#1](https://github.com/warioishere/sv2-apps/pull/1) coinbase-only JDC stalls after a chain-tip update; [#2](https://github.com/warioishere/sv2-apps/pull/2) `bitcoin_core_sv2` under-reserves coinbase block weight → `bad-blk-weight`).

**Method.** Five readers over the primaries (both implementation PRs, both bug PRs, Blitzpool `origin/main` `b48998f`, the Sep 10–11 comment thread) → five assessors, one per spec area → three adversarial refuters per finding (correctness / relevance / precision; majority rule) → one synthesizer. 33 findings, 13 survived, 20 refuted. Spec and roadmap edits below were applied the same day.

## Answer

Yes, but not where "change" usually means for a spec: no 0x0003 wire format, arithmetic, output order, or carrier text moves. PR #203's head is still its single commit 47dbedd (2026-09-10); warioishere's 2026-10-11 comment pins two fork implementations to exactly that commit, reports a mainnet interop run against Blitzpool's JDS (self-reported, no artifacts), and files two SRI bugs unrelated to 0x0003. Nobody has replied; the only activity since is two reactions.

What it changes for silent-pool (edits proposed):
1. Pins (spec §7.1, frontmatter, O10, roadmap Dependencies/R3/watch record): PR #203 by SHA 47dbedd instead of the "2026-09-15" date (that date was a comment edit, not a text change); and bitcoin_core_sv2 MUST be pinned past the `block_reserved_weight = max(1168 + 4*size, 2000)` fix (warioishere/sv2-apps#2, carried in #3) on both spc-pool (source = "ipc") and spc-agent's JDC — upstream main and v0.8.0 reserve only max(4*size, 2000), i.e. none of the 1168 WU of header/scriptSig/witness commitment once outputs exceed 208 B. That is the one real bug the mainnet run found, and §8.4's idle-mempool harness cannot catch it, so §8.4 gains a full-mempool step 9.
2. Roadmap Phase 4: spc-jdc becomes a fork of warioishere/sv2-apps@90b3e3d (+ warioishere/stratum@9be4023), which already implements every item in the old bullet and passes a 0-value OP_RETURN in additional_outputs through byte-for-byte; the remaining deltas are sp_address, the §3.6 own-P check, refuse-not-fallback on partial negotiation, and rebuilding (not re-sending) the stored Full-Template declaration when the distribution changes.
3. Corrections surfaced while checking the spec against the new code (not caused by the comment): §3.5's found-time "settlement invalidation" bullet is redundant and mis-timed (ledger moves at booking, as Blitzpool does); §11.9's conservation identity double-counts Σ ark + Δpending; §4.6 never says JD-mode settlement must read the mined coinbase (JDC pays at its own T) — stated as a rule plus new open item O11 on how `claim` is defined; §2.4.2's OP_RETURN costs 46 B / 184 WU, not 44 / 176 (roadmap 43 B figures likewise); §11.2 gets a one-paragraph note that silent-pool's weight_P shape is Blitzpool's ToPool composition, not the PPLNS ToOtherMiners shape warioishere described.

What does not change: the §3.5 struct/TLV/validation formula (byte-identical to stratum#1 and 47dbedd); the §2.4.2 carrier design; the §4.6/§11.1/§11.2 representation of sub-threshold value; the same-height grace rule (PR #203 §7.2-conformant; the reference JDC's old-id re-send is a fork delta); §2.4.1 and §4.8 text (protocol-layer; the shim bug lives in §7.1); the Blitzpool frontmatter pin 7815884 (correct provenance for the ported bp-pplns math; b48998f is recorded as a reading reference only); spc-jds remains a build (no SRI JDS implements 0x0003).

## Explicitly unchanged

- §3.5 SetPayoutDistribution struct, field types, TLV (0x0003/0x01, 8 B LE) and the validation formula (floor(weight·(T−F)/W), strict `<` dust prune, pay_P by subtraction, F ≥ T rejected): byte-identical to PR #203 @47dbedd §3.1/§4/§6 and to warioishere/stratum#1 coinbase_transaction_payouts.rs:43-55,158,172,173,183. No spec text has moved since 2026-09-10.
- §2.4.2 carrier design (0-value `OP_RETURN "SPc" A_send` in `additional_outputs[0]`): survives the reference JDC byte-for-byte (sv2-apps#3 payout_distribution.rs:98 clones additional_outputs after pool_payout + kept payouts; outputs() reserves them; unit test uses a 0-value 0x6a script) and Blitzpool's validator (requires value == 0, positioned between payouts and trailing outputs). Only the byte count sentence changes. Caveat: no JDS emits a non-empty additional_outputs today (Blitzpool sends vec![] everywhere), so spc-jds is the first.
- §4.6 custody statement, §11.1 rail policy and §11.2 table (sub-threshold value → weight_P in JD, → pay_P in pool-template): PR #203 §3.1 L55 ('MAY include value credited on behalf of miners not represented') and §9.3 L211 are unchanged; the JDC computes pay_P by subtraction and never inspects weight_P; the only pending text request (a §9.3 sentence that the pool output 'may but need not absorb the unrepresented value') would merely restate that both shapes are allowed. §11.1's 'trimmed-above-T → pending, wait a block' matches Blitzpool's 'fairness, never validity'.
- §3.5 same-height-only grace rule and the height-straddling MUST (R4): stays as written. It is a legitimate exercise of PR #203 §7.2 (grace is a JDS MAY). The reference JDC re-sends the stored Full-Template declaration with its old id at SetNewPrevHash and has no height tracking, but that is a fork delta (now in the roadmap spc-jdc bullet), not a spec change; no height field is added to distribution_id (see contested).
- §2.4.1 scriptSig text ('reserved by the Template Provider unconditionally'): unchanged. It is protocol-layer text destined for docs/spc-spec.md; the TDP mandates the 400 WU. The fact that the bitcoin-core-sv2 IPC shim violates the TDP is a dependency bug, handled by the §7.1 pin and §8.4 step 9, not by rewriting the BIP-bound paragraph.
- §4.8 weight budget / autoscaler ('fairness, never validity'): unchanged. Blitzpool's `ceil(budget/4) + 256` size derivation with coinbase structure inside the budget is immune to the shim bug, and §4.8 ports Blitzpool; the proposed outputs-only rewrite would have created the exposure it claimed to fix. The TP-side guarantee is pinned in §7.1 instead.
- §8.1, §8.2, §8.3 test lists: unchanged. stratum#1's compute_payout_amounts is not an independent oracle for spc-accounting (which emits weights, not sats, in JD mode) and would be the implementation under test once spc-jdc is forked from PR #3; the §8.3 validation assertions already exist as stated (Blitzpool src/jdp/payout_distribution.rs tests mutated/reordered/missing outputs; only height-straddling and the SPc carrier are new).
- §7.6 AGPL porting list: unchanged. No bp-stratum-v2 JDS code is ported; 0x0003 wire structs and math come from extensions_sv2 (MIT OR Apache-2.0) and the sv2-apps fork; §7.6's 'attribution in NOTICE' already covers anything copied later.
- Frontmatter pin `warioishere/blitzpool-server-rust @ 7815884`: unchanged. The spec cites Blitzpool only for bp-pplns ledger/trim/autoscaler/fingerprint/vouching, all present at 7815884 and matching the 2026-07-27 code reads; 7815884 already ships a 0x0003 JDS in the pre-#203 RequestPayoutOutputs form, so 'predates the 0x0003 JDS' was false. b48998f is recorded in UPSTREAM_DEPS as a reading reference only.
- Roadmap Decision 8 and R4: unchanged. 'MUST NOT declare across a height boundary' stays a JDC-own-tip rule implementable from the JDC's TP state.
- spc-jds remains a build on sv2-apps jd-server (§7.1, roadmap Phase 4 bullets 1–3): no SRI JDS implements 0x0003 (PR #3 touches zero jd-server files); Blitzpool's jdp/* is the only reference and is read, not ported.
- Roadmap Phase 4 estimate (≈ 4 weeks): left as is. A ≈3-week re-estimate is defensible once spc-jdc is a fork, but the proposed edit carried misplaced §7.1 SHA references and an unrequested spc-jds re-basing; the roadmap owner can trim after the fork decision.

## Findings refuted by verification (not applied)

- §2.4.2/§3.5 append about the 'SRI reference JDC' — refuted 2/3: third-party implementation status in a normative section, rots on merge, and 'SRI' misattributes an unmerged personal fork; nothing normative changes.
- §3.5 Grace-window JDC-side rule (two variants: 'treat current distribution stale at own SetNewPrevHash', 'wait for a carrier change') — refuted on precision: carrier change ⇔ height change is false (§2.2 mid-height restart), the 3-strike/pool-lag sentence is wrong in direction and reachability, and the behaviour is a fork delta — folded into the roadmap spc-jdc bullet instead.
- Encode height in distribution_id as (H<<32)|seq — refuted: the JDS already records (id, H) in spc:dist:current and parses BIP-34 height from coinbase_prefix; per-height seq breaks monotonicity on restarts/reorgs and trips the reference JDC's non-increasing-id fallback.
- §3.5 'Leak, stated' rewrite replacing 'sub-dust set' — refuted: the sub-dust set is the JDC-side dust-prune set (still correct, merely empty under §11.1); the edit inserted a chain-visible aggregate into a sentence about residue over chain observers.
- Roadmap 'signed pending ledger' wording and §4.6 heading 'wrong arm' — refuted: WithheldValue::ToPool does not exist at pinned 7815884 (introduced 2026-08-03), Blitzpool's ToPool mode has no ledger at all, and §7.6 already names suppress_matching_debits; roadmap L42/L81 describe Blitzpool's ledger, which is signed.
- §4.8 'fairness, never validity' rewrite with outputs-only budget — refuted: Blitzpool-style derivation is immune; the rewrite would have introduced the dependency on the TP formula; handled by §7.1 pin + §8.4 step 9.
- §2.4.1 'unconditionally' rewrite — refuted: protocol-layer text for BIP review; the proposed text cited a §7.1 fix that did not yet exist and over-generalised the threshold; the shim bug now lives in §7.1.
- §1/§8.4 'MUST cherry-pick sv2-apps#1' — refuted: inherited automatically by forking PR #3 (its first two commits are #1), and the proposed §8.4 case-2 assertion ('full subsidy to output 0') contradicts case 2's 0x0003 coinbase.
- Roadmap R3 'spec-drift risk went down; two implementations pin 47dbedd' — refuted: Blitzpool b48998f does not pin 47dbedd (still 'additional_outputs MUST be 0', no F term — a 04bac85-era reading), both forks share one author, the PR is open with the L168 question outstanding; only the date → SHA correction was kept.
- New roadmap risk R14 (fork-chain crate API churn: unbumped parsers_sv2/handlers_sv2 breaking changes, no upstream PR/CI) — refuted: the spec has no dependency on the fork chain yet and the mitigation duplicates R3/O10; noted inside the §7.1 pin paragraph instead.
- §7.6 NOTICE listing for ported Blitzpool 0x0003 JDS files — refuted: nothing from bp-stratum-v2 is ported; recompute math comes from extensions_sv2 (MIT/Apache); 'depended on, not ported' was also wrong for the forked jd-client/jd-server bins.
- Phase 4 ≈4 → ≈3 weeks re-estimate — refuted on precision: cited §7.1 SHAs that do not exist, re-based spc-jds on Blitzpool b48998f against its own 'JDS unchanged' claim, and presented a fork head as upstream.
- §3.5 'height-straddling is the steady state; pre-generate a_send[H+1] and publish distribution(H+1) alongside' — refuted: SRI defers the future-template send (not a pre-declaration), the fix contradicts §2.2 forward secrecy and PR #203's single-current-id model, and 'MUST NOT re-send' would strand activated jobs (Success handler needs the re-sent declaration).
- §8.3 harness-provenance sentence ('the four assertions are new code') — refuted: Blitzpool crates/bp-stratum-v2/src/jdp/payout_distribution.rs already unit-tests mutated/reordered/missing outputs and a non-empty 0-value additional_outputs; only height-straddling and the SPc carrier are new.
- §8.3 partial-negotiation matrix expansion — refuted: spec §3.2 L224 already mandates refusal; the text invented an `extension_negotiation_timeout` knob and a pool-side timeout neither PR #203 nor 0x0001 prescribes, and 'exit with a named error' conflicts with the §1 spc-agent consolidation; the fork's base-protocol continuation is recorded as a spc-jdc delta in the roadmap bullet.
- Move the frontmatter Blitzpool pin from 7815884 to b48998f — refuted: 7815884 is the correct provenance for the ported bp-pplns math (distribution.rs differs by ~1800 lines between the two); b48998f recorded in UPSTREAM_DEPS as the 0x0003 JDS reading reference only.
- §8.2 'extensions_sv2::compute_payout_amounts as independent oracle' — refuted: spc-accounting emits weights, not sats, in JD mode; the forked spc-jdc would call that very function (tautology); belongs at most in UPSTREAM_DEPS/§8.3.
- §3.5 'JDS-side height check unimplementable without a wire field' — refuted: the publisher assigns the id and holds H per id (§5.2 spc:dist:current); comparison to the BIP-34 height in coinbase_prefix is a direct equality.
